# Kite Card — Credit Card Acquisition Funnel Analysis (SQL)

An end-to-end funnel analysis of a fictional European neobank's credit-card product,
written in SQL (DuckDB). The goal: find where applicants drop out, which acquisition
channels actually pay back, and what operational factors drive card activation.

**Funnel:** application → KYC → credit decision → card delivery → activation → first transaction

> **Synthetic dataset** (20,000 applications, Jan–Jun 2025, generated by script). Business patterns were built into the data,
> so the findings are real for this dataset but say nothing about the actual market.

## Q5 — Why are applications declined?

File: [`sql/05_decline_reasons.sql`](sql/05_decline_reasons.sql)

| Reason | Type | Declines | Share of declines |
|---|---|---:|---:|
| insufficient_income | risk model | 1,897 | 23.5% |
| high_dti | risk model | 1,763 | 21.9% |
| adverse_history | risk model | 1,292 | 16.0% |
| income_unverified | process | 1,251 | 15.5% |
| thin_credit_file | risk model | 1,173 | 14.5% |
| policy_rule | policy | 690 | 8.6% |

- **Most declines are the risk model doing its job** (75.9%). Not a problem by itself; the dataset has no default data, so we cannot say whether the model is too strict.
- **"Income unverified" is a process problem, concentrated in one city.** In Valencia it is 58.9% of all declines; in other cities 7–12%. That points to the document-verification flow there, not to riskier applicants.
- **Manual review adds time, not judgement.** 18.5% of decisions go to manual review. Approval rate is the same as automated (52.7% vs 52.6%), but the median wait from KYC to decision is 52.6 h vs 0.2 h. Customers approved through manual review activate their card less often (50.4% vs 61.0%) — this is a correlation, consistent with lost momentum while waiting.

**Recommendation:** fix the income-document flow in Valencia first (cheapest win), then limit manual review to the cases where it actually changes the decision.

## Data model

| Table | Grain | Rows | Notes |
|-------|-------|------|-------|
| `customers` | one row per applicant | 20,000 | city, employment, income, birth year |
| `applications` | one row per application | 20,000 | channel, device, acquisition cost, KYC outcome |
| `credit_decisions` | one row per decided application | 17,009 | approved/declined, reason, automated vs manual, score version |
| `cards` | one row per approved application | 8,943 | shipping, courier, delivery, activation |
| `transactions` | one row per card transaction | 48,343 | amount, merchant category |

Relationships: `applications.customer_id → customers`, `credit_decisions.application_id → applications`,
`cards.application_id → applications`, `transactions.card_id → cards`.

## How to run

1. Install the [DuckDB CLI](https://duckdb.org/install) (Windows: `winget install DuckDB.cli`).
2. From the repository folder, build the database from CSV:
   `duckdb card_funnel.duckdb -c ".read sql/00_schema.sql"`
3. Open the notebook UI: `duckdb card_funnel.duckdb -ui`, then run any file from `sql/`.

## SQL techniques used

Multi-table joins, CTEs, conditional aggregation (`FILTER` / `CASE WHEN`), date arithmetic,
window functions (`LAG`, `ROW_NUMBER`), cohort analysis.
